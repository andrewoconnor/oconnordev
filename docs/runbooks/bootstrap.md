# Bootstrap and dependency ordering

1. Apply `infra/spacelift` first to create the stack graph and AWS integration. The account bootstrap roles must already exist because each account stack assumes its account's bootstrap role. This stack manages the shared Spacelift objects and child-stack dependencies.
2. For the staged cutover, `.spacelift/config.yml` (version 2) is keyed by immutable stack IDs. Keep existing stack `oconnordev-hermes` pointed at `infra/aws/tools`; do not create a replacement stack. Temporarily set `TF_VAR_retain_legacy_github_oidc_provider: "true"` for `oconnordev-production` while the new broker path is being tested. If the speculative GitHub-stack plan runs before the TOOLS output dependency exists, a temporary broker ARN input may be used only for that bootstrap plan.
3. With the true retention setting, PRODUCTION must keep the old OIDC provider at its moved `[0]` address and retain the exact old master-only GitHub OIDC trust statement, while adding the TOOLS broker trust statement. Review the plan and confirm no unintended resource replacement before applying.
4. Apply the TOOLS child stack under its existing ID (`oconnordev-hermes`) and confirm its outputs. Apply the `oconnordev` Spacelift administration stack to record address moves, update the display name/root path in place, and update dependencies; then apply PRODUCTION and the GitHub repository-configuration stack after their dependencies complete.
5. Run the site workflow on `master` and verify both role assumptions, S3 sync, and CloudFront invalidation succeed. The workflow-file change alone does not trigger a deployment.
6. After the chained workflow succeeds, remove the temporary environment overrides from `.spacelift/config.yml`, but keep the `oconnordev-hermes` root mapping to `infra/aws/tools`. The broker ARN must come only from the TOOLS dependency. With the Terraform default `false`, the PRODUCTION plan should remove the old direct-trust statement and destroy the old PRODUCTION OIDC provider; review and apply that cleanup separately. The in-code Spacelift stack remains authoritative for stack metadata.

Before applying the TOOLS root in a new environment, inspect account `421680664125` directly for both the `https://token.actions.githubusercontent.com` OIDC provider and the `oconnordev-github-actions-broker` role. The read-only AWS MCP caller is in SECURITY (`482921124454`); the organization Config aggregate queries returned zero rows for these exact TOOLS resources but do not establish their absence. If either object already exists outside TOOLS state, import/reconcile it at `aws_iam_openid_connect_provider.github_actions` or `aws_iam_role.github_actions_broker` rather than attempting a duplicate create. Before the first GitHub repository-configuration apply in a new environment, check whether `OCONNORDEV_TOOLS_GITHUB_ACTIONS_BROKER_ROLE_ARN` exists outside Terraform state; if it does, import it as `github_actions_variable.tools_github_actions_broker_role_arn` with provider ID `oconnordev:OCONNORDEV_TOOLS_GITHUB_ACTIONS_BROKER_ROLE_ARN` before applying.

## Existing audit state and the enable flag

The current General Spacelift state manages `aws_cloudtrail.organization[0]` and the management Config resources at their `[0]` addresses (recorder role, role-policy attachment, recorder, delivery channel, and recorder status). The stack has no explicit `TF_VAR_enable_management_account_audit` override, so the Terraform default `true` applies. Do not set it to `false` on this existing state: because the variable gates these resources with `count`, that would plan their deletion. Before any later change to the setting, re-read the live Spacelift state and plan; if the addresses or state have changed, stop and reconcile imports/state before proceeding.

For a new environment where an organization trail or any of the gated Config resources already exists outside Terraform state, import each existing resource into General before enabling the flag. In particular, the trail address is `aws_cloudtrail.organization[0]`; never repeat a historical `state rm`/import migration when the resource is already managed.
